# ADR 0004 — Release stages, progress and confirmation provenance

Status: Implemented under the user's milestone/ownership approval, 2026-11-06; user manual acceptance pending. Supersedes the personal stage-policy implementation restriction in ADRs 0001–0003 and earlier planning documents. The user explicitly authorized AI domain logic, tests, migrations, typed integration and UI, with reviewable changes and a stop before the next milestone.

- A project contains independent releases. Each starts with the original seven persisted stage instances and a real protected final-confirmation obligation. No sample work, historical releases, dates or statistics are seeded. Stable stage identities and reasoned exclusion are supported; full stage/template editing is deferred.
- Release membership is commitment. Suggestions remain visible project backlog until explicitly accepted. One action belongs to at most one release; stage reassignment within that release is allowed. Further-release work uses new actions rather than rewriting earlier scope. Confirmed releases are frozen; correction/withdrawal is a future audited operation. These consequential choices were explained before coding.
- Applicable committed actions count once. Included stages have equal weight; excluded stages do not contribute. Empty included stages or committed Unassigned actions produce null overall progress and visible scope review. Current stage is the first ordered stage with unfinished eligible work; ordinary later work can finish early. Progress is derived on main, never cached in SQLite or calculated again in React.
- Migration 002 adds releases, release_stages, release_actions, release_verifications and action_events beside the three existing tables. It does not rewrite projects/actions/checkpoints or invent past events. IDs/text/timestamps survive; old actions have no membership until accepted. Shipped 001 remains unchanged. The backup/transaction/version runner now also checks foreign-key consistency before commit. Composite keys and guards enforce ownership, protected items and frozen scope. Primary references: SQLite [foreign keys](https://www.sqlite.org/foreignkeys.html) and [triggers](https://www.sqlite.org/lang_createtrigger.html).
- Manual verification records contain the actual artifact/version identity, evidence reference, summary, passed/failed outcome, main-generated time and assessed scope revision. References are inert text; no file/command opening is added. Recording evidence does not change its own revision. Committed action/scope changes advance that release's revision, conservatively including edits to excluded work whose percentage stays unchanged.
- Confirmation requires the **latest** verification to be passed at the current release/revision, all ordinary applicable work complete and scope review resolved. An older pass cannot bypass a later failure. The protected action has no generic complete/reopen/exclude/move route; its displayed completion derives from the confirmed release, not actions.completed_at. Confirmation and its audit event commit atomically. No arbitrary 99% cap or rounded-number readiness gate.
- Manual provenance records the user's actual assessment, not independently authenticated artifacts or automatically executed tests. Automated runners, dependency-specific freshness, artifact authentication and publishing remain future work. The UI labels manual verification and does not claim independent software verification.
- Policy version 1 is stored per release and validated on reads. Future formula versions require an explicit compatibility/migration decision preserving confirmed results; no policy-plugin engine is added.
- openProject remains one authoritative project snapshot, now including releases/progress/evidence and action history. Release selection is a local view, avoiding a second query/cache. Write acknowledgement versus refresh failure handling is preserved: stale progress/Resume withheld, failed-write drafts retained, retry reads never resave.
- Seven named operations extend the six-method bridge. Identical sender/window/main-frame/exact-document checks and validated Result envelopes apply to all 13. Security preferences, protocol/navigation policy, data location, dependencies and package versions are unchanged. No generic SQL/IPC channel.

The user reviews policy, persistence, errors, security and manual acceptance. Remaining hard-to-reverse future decisions are correction/withdrawal of frozen releases, cross-release reuse, formula-version compatibility and automated provenance. No irreversible shortcut for them is implemented. Checkpoint journals and Resume remain project-scoped/append-only; per-action checkpoint links are deferred. Unsaved release drafts clear on project/release navigation; no dirty-draft warning system is added.

See [verification and file map](../verification.md). Stop after this focused slice; do not start workflows, publishing or the next milestone.
