## Project workspace information architecture

Use one durable project shell. Global Home and Workflows remain in the sidebar. Inside the project, **Overview → Sources → Engineering Map → Development → History** gives each destination a clear job. The arrows describe a first-run journey. Users can switch directly between views. **Resume** is a contextual entry from Home and Overview when there is a saved checkpoint. **Releases** remain a separately named delivery destination.

| User intent and destination | Shipped data or action | Proposed interaction and dependency |
| --- | --- | --- |
| **Home** · Choose a project or pick up a saved next step | Saved checkpoint, recorded activity, actual knowledge counts. Home owns the PTB chooser today. | Keep **Open project** and global blueprint preview. A project with a saved next step can expose a clearly labelled journal route now. V5a is the separate gate for Continue to an intentional record target. |
| **Project Overview** · Understand the project and find the next surface | Goal, actual counts, one formation receipt and capture summary. A plain project still has its working tools. | Keep a consistent header and project identity while switching views. Surface actual capture and journal entry points. Newly formed projects may still land on the Map. Keep an existing project or Continue entry in its relevant view when possible. |
| **Sources** · Find provenance or review a new capture | Stored files and diagnostics under Overview, with immutable exact-source reads. Review/apply creates a new project or opens the project already bound to the native PTB root. | First expose **Captured sources** using existing data and dialog. Later give Sources a project view grouped by binding and capture revision, with **Add source** behind a reviewed attachment policy. |
| **Engineering Map** · Explore components, features and related engineering records | Stable IDs, typed native edges, read-only inspector and exact spans. | Keep the atlas and focused neighborhood. Use a local trail such as **Engineering Map › Connections around [record]** and preserve explicit Back. Map actions expose context. Commitment and evidence have separate approvals. |
| **Development** · Plan or pick up work | Current tools contain ordinary backlog actions. Imported scopes, authored stage order and proposed actions are captured knowledge. | Later offer a date-free roadmap with optional scope and ordered stages, explicit Unassigned and unscoped views, and distinct Proposed and committed work. Inline stage order can be shown as a Draft plan. V3a1b/V3b1 are the gates for committed work and active scopes. No derived priority, dates or development percentage. |
| **History / Resume** · Recall what happened and return to work | Existing checkpoint history, project-level Resume, formation event and action audit. | Make the journal easy to find now. Later History groups actual events and user notes by project and links to record/revision only when that link exists. V5a enables linked targets and a sensible fallback when a target cannot be opened. |
| **Releases** · Inspect protected delivery and verification | Existing release workspace, release-scoped progress, workflow copies and frozen confirmation. | Keep a distinct delivery entry. Opening or adding a project source does not update release progress or confirmation. |

An existing project can start with a journal or ordinary actions and reach the Map only after it has a source graph. A first-run Vivarium user can review, form, read captured files, explore a requirement and save a project-level checkpoint today. A returning user should eventually open the explicitly saved record and see why it matters. That target is separate from the last node they happened to click.

## Future Add source and overlap review

1. From **Project → Sources**, choose **Add source**. The project target is explicit. Main selects a source through a native bounded grant and creates an immutable candidate capture with exact files, diagnostic spans and the selected adapter version.
2. Inspect the capture before deciding what to apply. Show already bound and unchanged, changed from the last reviewed capture, new candidate, possible match and conflicting assertions. Separate unsupported or invalid content. If the source is already bound to another project, show that binding and block silent reassignment. Keep both native IDs and the project's canonical IDs visible in the comparison where needed.
3. Compare previous reviewed source, current local revision and incoming capture side by side, with exact source links. Offer explicit **Link to existing**, **Keep separate as proposal**, or **Skip** for ambiguous new candidates. For a changed bound definition, offer **Keep local**, **Accept incoming as a reviewed revision**, or **Skip** according to the approved merge policy. Show both ends of a disputed relationship. Title or path similarity is a review cue, never identity.
4. Confirm the exact choices. A later main-owned transaction would check project ownership, expected revisions and conflicts, then write bindings/crosswalk and a receipt atomically. Preview and cancellation stay read-only. Keep old captures and original events, retain both provenances when explicitly linked, and preserve existing commitments, evidence and confirmed releases. Show unresolved candidates after partial review.

Storage already separates project, source binding, capture and entity IDs. The current runtime has one PTB formation path, a root-based receipt summary and no attach/update command or cross-source match policy. A multi-document PTB package is one source capture today. Multiple sources per project will need explicit adapter authority, crosswalk and source-specific revision rules. Ordinary Markdown can begin as inert document context. ## Proposed small implementation slice

One renderer-only pass in three reviewable parts, with the existing graph projection, React Flow, ELK, typed bridge, and stored-source modal.

1. **Graph and canvas.** Use measured bounds for explicit **Fit map**. Keep readable opening zoom with a coherent visible starting branch when the full atlas is larger. Make the current zoom and a return to readable scale clear. Pan and zoom change the camera. **Arrange** changes positions while keeping the camera. **Expand** places new cards beside their branch, then pans or fits that branch after measurement if needed. An explicit relationship pivot can reveal and pan to its target. Selection of a visible card, panel open/close and ordinary resizing preserve the current transform. Keep the bounded projection and communicate when connected records are available only in the outline. Reuse the drawer at medium width, a project-only navigation disclosure and full-width detail at narrow width. Hide or move the MiniMap when it would obstruct the compact canvas.
2. **Relationships, inspector and Back.** Improve tips and local label placement, using a readable edge-focused label when the canvas is crowded. Keep a full, keyboard-reachable inspector relationship row with endpoints, direction and the exact source action. Avoid a global edge layer above cards. Stack long fields, surface contextual source buttons and keep the actual modal untouched. Reset scroll and focus for a new record. Store one frame per explicit **Explore connections** with anchor, selected record, projection controls, card positions, camera, inspector scroll and stable focus target. **Back** pops one frame and restores it after the view is ready. Pending layout/reveal work cannot override that frame or a more recent drag or pan. Ordinary card selection does not add a history entry. Keep one history mechanism and defer a separate inspector-record history.
3. **Project entry points.** Use real **Captured sources** and **Journal & project tools** navigation from the knowledge workspace. Preserve the prior view and its state on return. Existing actions, checkpoints, audit and releases continue to use their established components. Show a Resume affordance only when saved context exists. With no checkpoint, the journal still offers checkpoint creation. No inactive tabs or placeholder scheduling controls.

Expected edit area is the knowledge workspace and its styles, the project navigation and existing journal entry points in the renderer, and focused Electron regression tests. **Backend work required for this slice is zero.** Current workspace reads expose the graph and captures, record and source reads provide stable references, and the existing checkpoint data provides project-level Resume. A linked Resume target, durable capture attachment/conflict review, new development transitions and real scheduling require their separately approved data and command contracts. Persistent personalization or native full-screen integration can be reviewed separately. ### Acceptance after approval

Run the flows on the rebuilt Windows app at **800 × 820**, **1160 × 820** and **1540 × 1000** outer window sizes. Use Vivarium, FieldLedger and a no-link or empty-map case. Screenshots accompany measured assertions and a visual inspection at each size.

| Journey | Required evidence |
| --- | --- |
| **Fit, zoom, pan and drag** | Drag a real card by its grip and assert the expected position change with a stable camera. Pointer-pan and use zoom controls, then assert the transform changes and the scale display agrees. Fit after expansion shows every rendered card inside the usable canvas with padding and preserves positions. Arrange moves a dragged card back into layout and preserves the camera. Test the readable scale recovery and stable selection through panel open/close. |
| **Expand and explicit reveal** | Expand **Procedural anatomy generation** by pointer and keyboard. Assert **Body silhouette and proportions** becomes visible within usable canvas bounds, its authored link remains, and cards already on the map keep their positions. | **Edge readability and responsiveness** | In the DNA action neighborhood, trace the direct **concerns feature** edge and the converging paths. Inspect marker placement relative to actual targets, label/card overlap and the keyboard-focused label at each size. Confirm full untruncated relationship text and direction in the inspector. Pan through the bottom-right region and verify chrome does not hide node actions in the compact layout. |
| **Back, scroll and keyboard** | On keyboard alone, enter the DNA action neighborhood, pivot to the feature and explore a second neighborhood. Rerun the relevant tests plus `npm test`, `npm run test:e2e`, `npm run package`, `npm run test:packaged`, and the knowledge UI journeys against the new executable. Use its capture comparison and explicit choices as future design input. Its saved context, staged commitments, match scores and conflict outcomes are illustrative. Resume depends on a saved checkpoint. The disabled Gantt and source/commit controls belong only in a future design until their operations and data exist. The fresh 1540 px outer-window run fits all six FieldLedger cards at the opening scale, while 1160 and 800 px clip the invoice feature. Inspector reading density and buried controls reproduce. Persistent scroll carryover on a different record needs a reproducing case before it is labelled a functional bug.
