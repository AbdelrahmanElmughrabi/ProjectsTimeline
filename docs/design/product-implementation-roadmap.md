V3a/3b split PTB's broad journey into reviewable end-to-end paths. Small projects need only V3a; they do not have to create scopes or adopt a lifecycle. The complex example then adds V3b. Basic source/decision/check definitions survive import before rich decision/evidence interactions ship; unsupported record kinds must never be silently discarded. V5a and V5b may be scheduled independently after their prerequisites, but only after each preceding delivered slice is reviewed. This is a dependency map, not permission to run parallel implementation now.

## Design and schema gates

Before V2: select maintained Markdown/strict-JSON tooling or justify existing standard facilities, review dependency/security implications; no installation is preauthorized. Before V3a: specify exact additive tables/keys/guards/DTOs, including uncommitted-action protection and source receipt idempotency; obtain SQL design approval before a new numbered migration. Before V3b/V4: approve scope/cardinality/progress and template purpose/key semantics. Never edit 001–003. Do not create all later snapshot/evidence/rule tables in an early migration.

Every persistence slice needs populated-v3 golden state (active and confirmed releases, templates, backlog completion, checkpoints/history), consistent backup, migration rollback/FK/newer-schema refusal, exact before/after comparisons and final packaged restart. Use temporary profiles; no production database mutation for testing.

Before code, rerun actual existing baseline. After each slice, run appropriate Node/domain/store and real Electron success/error/keyboard/compact checks; build/package and run packaged recovery for changed persistence paths. Include failed command, acknowledged command plus failed refresh, repeated read retry, stale revisions, duplicate apply and superseded navigation. Report actual outcomes separately from manual acceptance and from design-fixture checks.

Keep README/checklist/roadmap/verification/concise Obsidian checkpoint and relevant **new** ADRs current after approved decisions; preserve older ADRs as history. One integration owner coordinates migrations/shared contracts. The [Antigravity prompt](../antigravity-collaboration-prompt.md) remains review-first; implementation requires an assigned approved slice and isolated checkout/file ownership. Do not initiate implementation agents during this phase.

Git/Obsidian product integrations, local models, personalization, pattern recognition, automatic agents, workflow sync and advanced conditional rules remain future proposals. The current app remains the running product throughout; the reference image guides continuity, not fabricated controls or data.
