## Read models and mutation boundaries

These are **candidate responsibilities**, not a request to add every method at once. Reuse current Result/controller/main/store patterns; no generic graph service or renderer-side SQL.

| Surface / query | Minimum information | Mutation path / boundary |
| --- | --- | --- |
| Home / existing `getHomeSummary` extended only when needed | Project name/goal, latest real checkpoint, explicit target/focus and recorded attention | Existing creation/open; Continue resolves a saved link, not a guessed intention |
| Blueprint summary / existing preview + candidate prepared application | Human project/feature summary, validation separate from readiness, proposals/placements and exact effect counts | Native chooser → main capture → transient choices → main validation/plan → one atomic Apply/receipt |
| Overview / `getProjectOverview` | Goal, component/feature relationships, explicit commitment/work-state counts, chosen focus and saved next step | Adopt chosen proposals; local edit with expected revision; no automatic requirement acceptance |
| Development roadmap / `getDevelopmentView` | Optional scope lifecycle, authored stage order, current/proposed placements distinguished, unscoped/Unassigned | Explicit activation, adoption, start/complete/reopen, audited move; existing release commands cannot mutate these records |
| Map (Components/Features/Context lenses) / same graph projection | Component hierarchy, feature → requirements/actions → planned checks/decisions; direct versus indirect relation labels | Same action identity/commands as Development; no copied completion record per feature |
| History / `getDevelopmentHistory` | Real transition/checkpoint events, reason, current/historical target revisions | Read-only feed; source narrative does not become past events; paginated by stable event cursor |
| Inspector / `getRecordContext` | Definition/current revision, linked requirements/work, authored reasons, plan versus evidence, source disclosure | Purpose-specific edit/adopt/decision/check operations only when their slice ships; unavailable future behavior explained without inert buttons |
| Resume / `getResumeContext` | Exact checkpoint text, links, target/view/filter; missing/stale context status | Append checkpoint + validated context links atomically. Continue reads/resolves links; failed refresh retries reads only |

## Persistence and existing-code impact

- Current authority is schema v3: projects, actions/details, checkpoints, release/stage/evidence/history records and workflow templates. No durable PTB source binding or development graph exists yet.
- First formation needs reviewed **additive** source/capture/binding/receipt records; permanent components/features/requirement revisions/typed relationships; development action context/commitment; actual events. Preserve proposed decisions/check definitions and draft scope plans without interpreting them as accepted decisions, runs or activated scopes. Concrete tables/constraints need review; this is not approval to build all later evidence/snapshot tables.
- Linked recovery needs optional checkpoint context/target links. Inline activation additionally needs independent development scope/stage instances and membership history. Local work states/blockers need explicit transition semantics before storage. Never repurpose `release_stages` or make release-bound actions development members.
- Shared contracts → preload/main command allowlist → main validation → store transaction → controller acknowledgement → shared views change together in each slice. Revised V3a1a has no ordinary action rows/mapping for proposals, so no legacy query filtering/guard change. Before V3a1b reuses ordinary work, its mapping must enforce development lifecycle and release insertion/update isolation; hiding a checkbox is insufficient.
- Keep V2 occurrence/document/source selection distinct from durable internal record IDs. External PTB IDs map within a bound project; identical IDs in unrelated projects cannot select or mutate each other. Main validates every typed same-project link and expected revision.
- Concrete migration review must include populated legacy projects, unbound backlog actions, active/confirmed releases, workflow origins, completion/history and checkpoints. No conversion or invented historical events. V2 sessions remain non-mutating.
