# ProjectsTimeline engineering workflow

Use this process for meaningful changes. A small documentation correction can use a short scope and verification note. A migration, trust-boundary change or new milestone needs explicit approval and failure/recovery criteria.

## Workflow selection

Select the appropriate path from an ordinary development request and complete routine engineering activities within its authorized scope without procedural reminders. Read the context needed to identify expected behavior, affected callers and components, important risks and verification needs. Resolve consequential ambiguities before dependent work.

| Work | Approach |
| --- | --- |
| Localized correction | Inspect the affected code or document, change narrowly, run the relevant check and review the diff. |
| Bug | Reproduce the behavior, trace callers and root cause, fix the shared cause and run appropriate regression checks. |
| Meaningful feature | Reuse relevant specifications and decisions, then use the installed Spec Kit skills for specification, planning, tasks and consistency analysis before authorized implementation. |
| Schema, architecture or security-boundary change | Gather compatibility, failure and recovery evidence and obtain the existing required owner decisions before implementation. |
| Workflow or tool adoption | Inspect existing capabilities and propose the smallest integration. Repeat this adoption audit when the adoption task requires it. |

## Native Spec Kit

Use the skills exposed by the installed integration. For Codex, these are `$speckit-specify`, `$speckit-clarify`, `$speckit-plan`, `$speckit-tasks`, `$speckit-analyze` and `$speckit-implement`, invoked in the agent session. The `specify` CLI manages installation and configuration. Verify a capability locally before relying on it.

- Read the [project constitution](../.specify/memory/constitution.md) with the approved issue or scope and relevant ADRs. Reuse existing project designs as context and references for the bounded feature's artifacts. The roadmap owns milestone sequence and approvals, GitHub Issues track shared commitments and `tasks.md` decomposes implementation work.
- For meaningful feature work, use specify, clarify material gaps where needed, plan, tasks and analyze, then implement within the approved scope. Record required regression, IPC, migration and recovery checks in the feature specification so task generation includes them. Use `$speckit-converge` when a post-implementation comparison against the feature artifacts is warranted, and resolve confirmed in-scope gaps.
- Existing feature artifacts can be resumed at the appropriate step after checking their freshness. Spec directory names and Git branch names can differ in the installed version. Preserve the existing branch conventions.
- Checklists generated by `$speckit-checklist` assess requirements quality. Implementation tasks, executed verification and owner acceptance have their own records. Respect the installed skill's checklist review gates.
- Use the current bug-investigation path for fixes. Select optional skills and research according to the actual need. One main agent handles routine work, and independent collaboration follows the authorization and handoff rules below.
- If a required skill, artifact or configuration is unavailable or fails, report the specific gap and complete unaffected authorized work. An installed command or written instruction establishes availability or guidance. Actual execution and technical checks establish evidence.

## From issue to close

1. **Issue → Plan.** Record the user problem, expected behavior, constraints, acceptance and checks using the [issue template](../.github/ISSUE_TEMPLATE/engineering-change.md). A local draft is enough before publication approval. Use an existing real issue when available. Suggested labels are `feature`, `bug`, `ux-accessibility`, `tech-debt` and `testing`.
2. **Branch → Implementation.** Record the intended base and its exact commit, inspect the branch, status and worktrees, and preserve unrelated changes. Use a descriptive name such as `codex/v5a-linked-continuity` when a new branch is authorized. Commit complete, reviewable pieces with the existing `feat:`, `fix:`, `test:` or `docs:` style. Review migrations, contracts and security boundaries before changing them.
3. **Tests → Pull request.** Run checks matched to the change. Link exact evidence, distinguish reruns from prior results, and record open manual checks. Prepare the [PR template](../.github/pull_request_template.md) locally until the owner authorizes publication. Link a real issue where applicable. Use a closing keyword only when a PR targeting the default branch resolves that issue. [GitHub issue-linking rules](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue).
4. **CI → Review.** Once approved and enabled, Actions independently verifies the PR revision. Until then record actual local results. The owner reviews acceptance, tradeoffs and remaining manual checks. Rerun relevant checks after meaningful changes. [CI proposal](github-ci-proposal.md).
5. **Approved merge → Close issue.** Merge only on explicit owner authorization after review and applicable checks. Confirm the intended change landed before closing a real issue. Leave partially addressed issues open. Never reset, push, force-push, merge, publish or change remote settings without explicit authorization.

## Roles and isolated review

| Role | Responsibility |
| --- | --- |
| Product owner | Prioritize, approve decisions and scope, review and accept, authorize publishing and merge. |
| Product and architecture discussion | Explore vision, user flows, priorities and tradeoffs, then propose scope and acceptance for the owner's decision. This is a planning activity within the existing workflow. |
| Codex | Implement the approved scope, verify it, keep records current and prepare reviewable local commits. |
| Antigravity | Optional independent UX review with owner authorization in an isolated worktree. |
| GitHub Actions | Independent automated verification once approved. |

Codex is the integration owner and reviews delivered work. If an independent reviewer is useful, record a frozen base SHA, task, branch/worktree, exclusive write paths, approval gate and expected evidence. Have the reviewer return exact refs, checks and open findings. Keep research/prototype commits isolated unless explicitly reviewed for integration. Existing [V2 collaboration](agent-handoffs/v2-collaboration.md) is a worked example. Routine changes stay in one checkout.

## Verification and owner review

- Docs or process changes need link and diff checks. Code changes use the smallest relevant tests and normal build. Changes to IPC, migration, Electron navigation or recovery exercise the actual boundary and a populated isolated profile where relevant. Follow milestone acceptance criteria and use rebuilt packaging when the shipped path matters.
- Before reporting completion, review the diff and connected callers against the requested behavior, regressions, maintainability and affected security boundaries. Investigate check failures and finish authorized corrections. Report checks as Passed, Failed, Blocked, Not run or N/A with the revision, commands and useful evidence. Distinguish local implementation, hosted CI, owner acceptance, merge and publication status.
- For a meaningful milestone, name the important files and one architectural tradeoff. Trace one user action from UI → named preload/IPC → main validation/domain → SQLite → acknowledgement and refreshed read. Show one failure or recovery test and give the owner a small exercise, such as tracing a retry to confirm it performs only reads after a successful write.
- Record milestone status in the [roadmap](design/product-implementation-roadmap.md) and [checklist](engineering-checklist.md). Keep evidence in the [verification record](verification.md), consequential approved decisions in ADRs, and deferred ideas in the [visual backlog](design/visual-engineering-backlog.md). The Obsidian log is a short checkpoint with decisions, evidence, blockers, next step and a useful technical note when applicable.
- At meaningful pauses, leave the goal, issue or spec reference, relevant files and revision, actual checks, blockers, outstanding decisions and next authorized action in the existing state or verification record. A fresh session verifies that record against Git and accessible GitHub state before continuing.

Use the existing commands according to the affected behavior.

| Check | Command and scope |
| --- | --- |
| Documentation or instructions | Check changed Markdown links and anchors, preservation of existing instructions and `git diff --check`. |
| TypeScript only | `npm run typecheck` checks both TypeScript targets. |
| Node, domain, SQLite and build | `npm test` builds both TypeScript targets and the renderer, then runs the Node suites. |
| Real Electron interaction | `npm run test:e2e` rebuilds and runs the Electron suites with isolated profiles. |
| Packaged recovery | `npm run package` followed by `npm run test:packaged` tests the rebuilt Windows package. Follow the milestone's additional packaged-journey requirements. |

## V0.2 behavior trial

After the integration is reviewed, observe ordinary requests for a concrete small bug and an approved bounded feature, then test resuming interrupted work in a fresh session. Record workflow selection, actual skill use, checks, diff review, continuity, necessary approvals, reminders and unnecessary work in the [verification record](verification.md). Claim behavioral improvement only from observed trial results. Existing tests and CI supply technical evidence for the revisions they execute.
