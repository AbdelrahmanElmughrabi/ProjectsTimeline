## Approved UI data-refresh strategy — implemented for Resume

The original App applied mutation rows locally and sorted checkpoints again in React. The approved Resume implementation replaces that with one workspace query snapshot; independent panels no longer choose their own latest checkpoint.

useProjectWorkspace owns the selected project's read snapshot, request state and mutation handling. Form drafts stay separate. SQLite remains authoritative; no persistent project-data mirror exists in localStorage. Main computes Resume through its tested domain selector. Future progress/readiness policies will join the query only after their own approval/implementation. Child components render the snapshot and send named commands.

After a successful command, re-query openProject and replace the selected snapshot. Refresh the project list after project creation/promotion; on project navigation load a fresh snapshot. This adds a small local read but avoids maintaining several dependent frontend caches. Do not add a state library for this slice.

- Failed write: no saved indicator; retain inputs and old confirmed snapshot; allow explicit retry.
- Committed write + successful refresh: clear submitted draft, show confirmed saved state, update Resume/progress/summary together.
- Committed write + failed refresh: say **Saved, but could not refresh**; clear the submitted draft, mark the old snapshot stale, offer **Retry loading** only. Do not automatically repeat the write or show stale summary as current.
- Disable conflicting commands during write/refresh and guard responses by selected project/request identity, so an older response cannot overwrite a newly opened project. Handle read failures separately from write failures.

This is a localized renderer/query-contract change, not an Electron/process rewrite. Current explicit saves remain; today switching projects discards unsaved action/checkpoint drafts. A dirty-draft warning can be designed with the later navigation slice; do not silently introduce autosave.

## Resume Development — approved and implemented

Implemented scope: one prominent panel on the current project screen showing latest saved accomplishment, saved nextSteps and its real timestamp. No action/stage inference, automatic project reopening, external session restoration or editor launch. Empty-state control focuses the checkpoint form; Continue with actions focuses the action form. See ADR 0002 and verification.md.

Path: existing checkpoint model → pure selector and store query → ProjectDetail.resume → ResumePanel/useProjectWorkspace/App → unit/integration/Electron/packaged verification. Schema v1, migration 001, dependencies and preload/channels/security remain unchanged.

The user approved all six criteria below in the Continue Implementation brief. Criteria 1–5 have automated evidence; criterion 6 awaits user manual acceptance.

1. No checkpoint produces an empty Resume state without fabricated text/dates or a disabled-looking fake action.
2. Latest checkpoint is selected by createdAt descending, then ID descending; saved nextSteps is displayed exactly as stored. No pending action is silently chosen as its meaning.
3. Saving a checkpoint updates history and Resume from one authoritative query; selecting another project never shows the previous project's resume context.
4. An actual failed write retains both draft fields and leaves Resume unchanged. A committed save followed by failed refresh reports the two outcomes accurately; Retry loading performs no duplicate write.
5. A full restart of development and packaged builds restores the same saved Resume context, and all existing project/action/checkpoint/error/security scenarios still pass.
6. User reviews behavior and manually checks save → navigate → restart → resume. New feature state advances beyond Undecided only after user acceptance of design, and to Verified only with recorded evidence.
